# Pre-verdict protected-state owner contract

This draft changes one primary trust boundary: **transaction and history evidence for protected proposed state**. It supplies exact input records and a callable offline checker for the AssertionRecord domain verifier in OFARM #47. It does not change claim meaning, authority selection, assertion-act sources, Event Ingress classification, key custody, database roles or runtime transaction implementation.

The source decisions are pinned verbatim in `source-pins.json`: PR23 sections 5.5, 9–12, the transaction RFC sections 8–9 and 15, and the existing write-boundary and time-policy proposals. Their draft status remains unchanged. The actual existing transaction schema is copied without alteration; its `attemptContext` definition is referenced directly. Using that common context shape does not extend the existing operation-only NOT_REQUIRED profile to structure or compliance actions. Each caller must select its actual governed transaction profile independently.

## Evidence order and independent selection

The order is transaction-start snapshot, immutable input resolution, proposed assertion bytes, pre-verdict guard observations, domain verdict, and then the existing owner's checkpoint/finalization/receipt/atomic commit steps. This proof never requires the current attempt's later verdict, receipt, checkpoint or consumption record. Closed schemas prohibit inserting such fields. Original prior creation/ingress source records must be committed and visible at the transaction-start snapshot. A governed prior receipt also carries its original creator attempt, which must differ from the current attempt. Legacy ingress does not need an invented transaction-attempt identifier; if an original one is supplied, it is preserved and checked.

The caller selects the raw contract, context and guard-policy hashes independently of the offered proof, and selects the offered proof's immutable binding. The context identifies one trusted storage owner, the exact existing attempt context, intent and proposed result bytes, action, transaction/time-policy records, required immutable reads, negative reads, set reads and optional prior record. The proof cannot choose a different context, snapshot, policy or read set. Hashes detect substitution; they do not authenticate an owner. A production caller must obtain these selections from the trusted transaction/storage owner, never from the submitter. Fictional offline fixtures make that assumption explicit.

The snapshot is a concrete owner record, identified by the exact `attempt.transactionSnapshot` binding. Its positive observations state that exact record bytes were committed and visible at transaction start. Negative and set observations include exact predicates and storage guard versions. `snapshotToken` is an opaque snapshot identity, not a new canonical history position or general history watermark. A timestamp alone cannot establish membership. The checker rejects later/uncommitted visibility labels and mismatched attempts, boundaries or versions.

## Guard and write coverage

This revision specifies the optimistic compare-and-commit proof mode. It requires equal snapshot and observed versions for every required immutable read, absence predicate, set predicate and the proposed-ID absence guard. The proof carries the entire pre-verdict domain write set: exactly one INSERT of the exact proposed AssertionRecord. Updates, deletes, extra assertions, event envelopes, current-state writes and any other domain write fail. Later transaction evidence writes remain governed by the transaction owner's existing protocol and are not claimed to exist in this earlier record.

The consuming domain contract derives and checks the complete list of its immutable inputs against `requiredReads`. Each selected read has an explicit availability posture. `COMMITTED_AT_TRANSACTION_START` requires a positive start-snapshot observation and unchanged row version. `FIXED_BEFORE_DOMAIN_VERDICT` instead requires the exact independently selected fixed-input version and unchanged original bytes. This second route preserves inputs produced during validation, including Event Ingress proofs, without falsely claiming that they already existed at transaction start. The prior AssertionRecord itself always requires the first route; a new extraction of its older immutable creation evidence may use the second. Snapshot set members always require committed positive reads.

This division is explicit: a caller-supplied shortened manifest cannot establish complete domain coverage merely by passing the storage checker. The consumer must compare its independently derived full input manifest. Required set and negative reads likewise come from the independently selected transaction context. No generic admitted flag, arbitrary callback or opaque receipt substitutes for a check.

Reevaluation is allowed only with identical context, snapshot, proof and input bytes in the same attempt. It creates no admission, replay reservation or new commit permission. Reuse in another attempt fails. Every guard must still be rechecked and protected through the actual commit by the runtime transaction owner. An offline PASS establishes only conditional conformance of the supplied pre-verdict observations; it cannot prove database isolation, actual guard continuity, trusted clock provenance or actual atomic commit.

## Prior creation context

The new `priorAssertionCreationContextEvidence` is a storage-owner extraction record. It binds the exact prior AssertionRecord and the original immutable creation or ingress source bytes. Each extracted fact (creation route, prior record binding, typed governance boundary/twin, recorded anchors, and creator attempt when present) has an exact JSON pointer into those source bytes. The required `sourceDerivations.creationKind` selects the exact `PRIOR_GOVERNED_RECEIPT` or `LEGACY_IMMUTABLE_INGRESS` value from a committed original source. An extraction cannot relabel the route while keeping that source unchanged. If an existing original cannot supply the selected route, the owner must provide its actual governed source contract and evidence; the consumer cannot add a route label to the original or infer it from a ref. The checker verifies those selectors, original raw hashes and whole-object JCS bindings, rejects ambiguous/duplicate sources, and compares the extracted governance context to the independently selected current context. It never infers tenant/twin from an ID, current location, scope ancestry or claim content.

`PRIOR_GOVERNED_RECEIPT` and `LEGACY_IMMUTABLE_INGRESS` distinguish the source route. This extraction record is not itself a receipt or authorization decision, and does not reevaluate the earlier authority gate. The trusted storage/creation owner supplies an immutable derivation of the source context under its selected source contract. Source receipt and authority validity remain that owner's obligation. The domain consumer checks supported prior AssertionRecord schema, subtype, logical subject, authority-anchor equality, distinct IDs and correction posture. The storage proof establishes the precise source bytes and their transaction-start visibility; it does not replace the domain comparisons.

## Wire and digest rules

Control records, structured core inputs and `JCS_JSON` reads are original UTF-8 I-JSON bytes: no BOM, duplicate object keys, non-finite numbers, invalid Unicode, unsafe integers or excessive depth/size. Their object bindings are SHA-256 of RFC 8785 JCS with no exclusions, and `rawSha256` additionally pins the original bytes. The contract's self digest excludes only its own top-level `contractDigest`. Schema, source and checker pins use raw bytes. Resolution is local and closed; there is no network schema lookup. The existing attempt timestamps keep their canonical UTC spelling, precision and calendar checks; a deadline must be after the start. The checker does not replace the actual transaction time-policy evaluator.

Every required read, positive snapshot observation and read guard supports `digestMode: JCS_JSON | RAW_BYTES`. Omission means `JCS_JSON`; existing JSON wire records retain that interpretation. A `RAW_BYTES` binding is `{ref, revisionRef?}` with no `digest`, and `rawSha256` is its sole content pin. Arbitrary original bytes, including non-UTF-8, empty records and non-I-JSON source documents, remain unchanged. No wrapper, canonicalization, text conversion, rounded integer or raw hash in a JCS field is permitted. The 2 MiB per-input and 16 MiB bundle limits still apply.

The selected ref, optional revision selector, effective digest mode and raw pin must agree exactly across the required read, observation and guard. `revisionRef` in a binding is supported; the outer read/observation/guard selector is retained for compatibility. If both selectors occur they must agree, and their exact placement is retained and compared. Each ref has one mode, availability and selected version throughout an attempt, even when it serves several roles. A raw read requires the same committed snapshot/row-version checks or fixed-input-version checks as a JSON read. A guarded context containing hashes does not transitively guard its originals.

`EFFECT_INTENT`, `TRANSACTION_PROFILE`, `TRANSACTION_TIME_POLICY`, `PRIOR_ASSERTION`, `PRIOR_CREATION_EVIDENCE`, the proposed assertion, and creation `sourceRecords` remain structured JSON inputs. Raw mode cannot bypass their object or source-pointer duties. A committed raw set member is `{ref, revisionRef?, digestMode: RAW_BYTES, rawSha256}`; it must resolve to an exactly matching positive read and guard. Fixed inputs cannot be snapshot set members.

Successful `facts.readBindings` preserve the full selected read: key, role, exact binding and optional revision selector, effective digest mode, raw pin, availability, fixed input version where applicable, and the matching observed/snapshot guard versions. Consumers compare these facts with their independently derived manifest. Facts do not hide role or revision differences behind a context digest. Successful correction facts also expose the source-derived `priorCreationKind`.

## Later-artifact exclusion and owner responsibilities

The protected-state maintainer owns the read-mode, guard, facts and creation-extraction checks. The independently selected transaction/storage owner (`storageOwnerRef`) owns truthful availability before the verdict for every selected input, including opaque bytes and source-specific encodings. The checker rejects recognized current-attempt receipt/consumption/transaction-result labels and checkpoint or gate shapes tied to the current attempt. It also detects those JSON shapes inside a `RAW_BYTES` selection without using the decoded value as the raw content binding. A prior-attempt source remains eligible for the separate committed-source checks; recognizing its shape does not authenticate it.

Shape recognition is bounded. It cannot prove that an arbitrary opaque document, encrypted payload or unknown future schema is not a later artifact. The transaction/storage owner must exclude such dependencies when selecting the immutable context; the consuming domain owner must derive the complete required manifest and retain missing/unsupported dispositions. Neither owner may claim actual temporal availability from a caller label or hash. The source-creation owner retains source-route validity and original source admission. These responsibilities do not introduce new runtime enforcement or change another owner's schema.

The review publisher owns validation fidelity. The historical 94-case review is a locally retained result; its complete script and input archive were not published with the original PR, so it is not independently replayable from that PR and is not current repair validation. The published `run_review_repair_02.py` regenerates the new authored cases and can retain every exact input and output for CLI replay. A fresh review must inspect the repaired package independently; authored regressions are not independent approval.

The callable interface is `verify_state(proof_bytes, *, package_root, selected, context_bytes, policy_bytes, snapshot_bytes, records)`. `records` maps exact refs to original bytes, including the proposed assertion. Results use `CONDITIONAL_CONFORMANCE_PASS`, `FAIL`, `INPUT_ERROR` or `DEPENDENCY_UNAVAILABLE`, always with `runtimeProtection=NOT_ESTABLISHED` and `laterTransactionGate=NOT_EVALUATED`. A successful report exposes only exact bound facts for the domain consumer. It does not expose a reusable admitted Boolean.

## Construction and review

Acceptance requires independently replayed positive and hostile cases for all three action labels, initial and correction postures, supported prior routes, changed bytes, wrong context/attempt/policy/snapshot, incomplete guards, negative and set membership, duplicate proposed IDs, additional writes, cyclic later evidence and invalid input. Event and measurement content is retained byte-for-byte as opaque domain content here; its meaning is checked by #47 and the corresponding source owners.
